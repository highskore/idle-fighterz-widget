# Developing Idle FighterZ

## Build from source

The game is [highskore/idle-fighterz](https://github.com/highskore/idle-fighterz), a submodule at `game/`. You need Node and Rust, plus Xcode's command line tools on macOS, the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) on Windows (MSVC build tools; WebView2 ships with Windows 10 and 11), and on Debian/Ubuntu `sudo apt install libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev libssl-dev patchelf`.

```sh
git clone --recurse-submodules https://github.com/highskore/idle-fighterz-widget.git && cd idle-fighterz-widget
npm ci
npm run build               # widget page, then the release bundles for this OS
# macOS   → src-tauri/target/release/bundle/macos/Idle FighterZ.app (ad-hoc signed)
# Windows → src-tauri/target/release/bundle/nsis/*-setup.exe and bundle/msi/*.msi
# Linux   → src-tauri/target/release/bundle/appimage/*.AppImage and bundle/deb/*.deb
```

On Windows, clone with `git -c core.autocrlf=false clone …`: the page build matches the game's sources on LF line endings. Which bundles each OS makes is set in `src-tauri/tauri.windows.conf.json` and `tauri.linux.conf.json`, which tauri merges over `tauri.conf.json`.

In an existing clone, `git submodule update --init` fetches the game; `git submodule update --remote game` moves it to the game's latest commit (commit the new pointer).

- **Page**: `node game/build.mjs --widget` (`npm run page`) writes `dist/index.html` under the directory it runs from (here the repo root). It's the same page with `<html class="widget">`, the code fenced by `/*widget*/…/*/widget*/` in `game/page.html`, `game/game.js` and `game/world.js` kept, `game/widget.css` and `game/widget.js` filled in, no CDN three.js (only the title used it) and the fonts inlined from `@fontsource` in the local `node_modules`. The site build drops the fenced code, so the homepage doesn't change.
- **Floating** (the default mode): the game starts at once, with no title, links or card, and no sky or backdrop in any scene. Solid sprites get a 1px dark rim so they read on any wallpaper. Nothing fades at the window edges; instead the scene has room: the planet keeps the site's size against the sprites (56–70 px across its radius, as on phones and desktops), the pixel art is 1× below 520 pt and 2× from there, and the window is big enough round it for the giant ape, Nappa and the raids. Clouds, if on (always, while the pointer is over the widget, or never), are a finite cloud of whole outlined puffs in one of these shapes: drifting puffs (the default), whose cloud amount slider (1–5, default 2) adds clouds from a ranked list of spots clear of the planet and the hero's path, from three clouds up to a full scattered sea; every cloud is one of seven hand-made cumulus templates (checked by `npm run clouds`, which also draws them all on a contact sheet), mirrored and scaled per spot; or dock clouds (staggered rows along the dock like the site's cloud sea), a bank under the planet, a halo round it, or a plate it rests on.
- **Window mode** (a setting, live): an opaque rounded card with the site's skies, cloud sea and world backdrops, a shadow, and a free resize.
- **HUD**: five layouts. Dock (the default) is one pill under the planet with the power level, the form and a thin bar to the next one, dragon balls and wishes once there are any, and round icon buttons; floating, the game canvas stops above it so nothing runs under it. Also ring, pill bar, corner chips and top strip. It shows while the pointer is over the window and fades after a few idle seconds, or it can stay up. The frame rate is a setting: balanced (the default) draws at 30fps, 60 while the pointer is over the widget; smooth draws at 60 always; battery saver at 15, 30 with the pointer over it. The game runs at the same speed at every rate: battery saver steps the frame in between without drawing it. The per-pixel loops (the planet, outlines, the rim) run in WebAssembly from the game repo (`game/wasm`), which is why the CSP allows `wasm-unsafe-eval`; without it the same JS loops draw the same pixels. The ki training tree, angels, achievements and characters scroll down in one column, never sideways.
- **Skins and theme** (settings; `skin`, `theme`): classic is the five layouts above, and the default. Scouter puts the power level in a green glass lens (the only pixel text) with the buttons on its dark housing; Capsule Corp is a white enamel panel with an 8-capsule gauge and a blue button tray; the side drawer has a power chip, the buttons bottom left, and a tab on the right edge that slides out upgrades, the ki tree and heroes while the planet steps aside. The theme (light, the default; dark; auto, following the system) recolours classic and the drawer; the scouter is always dark and Capsule Corp always light. Both apply live. The skins live in the game repo (`game/skins.js`, `game/skins.css`).
- **Settings** (the gear in the widget, or Settings… in the menu bar): a search field at the top (focused on open; it matches labels, section names and synonyms, so "transparent" finds opacity; ↓ or Enter goes to the first match, Esc clears it, Esc again closes), always on top, size (a slider from 300 to 720 pt that snaps to the old small 300, medium 400 and large 560 within 16 pt, and is otherwise even, so 2× pixel art stays whole pixels; a saved `"size": "medium"` reads as 400), layout, skin, theme, HUD, frame rate, mode, clouds, their shape and amount, opacity, the show/hide shortcut, the power level in the menu bar, the tray icon's colour (Windows and Linux), launch at login, and quit. Notifications for villain raids, the dragon, trips, space pods and ascend each get their own toggle, plus quiet hours. Settings are saved to `settings.json` in the app's config folder: `~/Library/Application Support/com.highskore.idlefighterz/` on macOS, `%APPDATA%\com.highskore.idlefighterz\` on Windows, `~/.config/com.highskore.idlefighterz/` on Linux.
- **Windows and Linux**: the same widget, settings and menu, from a tray icon: the same scouter, black on a light taskbar and white on a dark one (Windows: the taskbar's own theme, `SystemUsesLightTheme`; Linux: the freedesktop portal's color scheme, else the GTK theme's name, and white when neither says, as most panels are dark). It follows theme changes within a few seconds. Settings has "tray icon: auto / light / dark" there (not on macOS, whose template image tints itself): auto is that detection, light is always the white scouter (for dark taskbars), dark always the black one; a pick applies at once and is saved as `tray_icon`. The shortcut is **Ctrl+Alt+P**, and settings spell keys out (Ctrl+Alt+P) where macOS shows ⌥⌘P. The power level goes in the tray icon's tooltip on Windows, which has no tray titles, and on Linux in an AppIndicator label (AppIndicator has no tooltip) and the tray menu's first item. Notifications go through the system's own (Windows toasts, the freedesktop notification service), which ask no permission up front. Launch at login is a `Run` registry entry on Windows and `~/.config/autostart/` on Linux (pointing at the AppImage itself, not its temporary mount). That entry's `Exec` line comes from the autostart plugin (auto-launch) unquoted, so it breaks for an AppImage whose path has a space in it, and for one moved after launch at login was turned on: keep it at a path without spaces (the installer's `~/.local/bin/idle-fighterz` is fine), and after moving it, turn launch at login off and on again. Opening the app again shows the running widget instead of starting a second one. On Wayland the show/hide shortcut isn't bound: global-hotkey (behind the global-shortcut plugin) is an X11 key grab that would fire only while an XWayland window has focus, so settings says so instead. Hover: Windows and X11 report the pointer as on macOS; Wayland tells apps neither where the pointer nor where their window is, so there the widget relies on the pointer events its page gets anyway.
- **No menu bar needed**: on a notched Mac, or behind a menu-bar manager, the icon may be out of sight. Everything works without it: the gear opens settings, × hides the widget, **⌥⌘P** (a global shortcut, changeable or off in settings) shows and hides it, and opening the app again (Spotlight, Finder, `open -a "Idle FighterZ"`) brings it back. A click on a notification shows the widget too. The menu-bar icon is a template image (a pixel-art scouter, 18×18 doubled to 36px for 18pt), so macOS tints it for light and dark menu bars.
- **Notifications** go through `UNUserNotificationCenter`. macOS asks once: when a notification toggle is first switched on in settings, or when the first one is due. Settings shows the answer (allowed, not asked yet, blocked) with a button to ask or to open System Settings. None go out in quiet hours, none while the pointer is over the widget (you're looking at it), and each kind at most once a minute. They need the app to run from its `.app` bundle and to be signed, ad-hoc at least; `tauri dev` runs a bare binary and shows none.
- **Hidden**: × hides the widget. With any notification on, or the power level in the menu bar, the game keeps playing while hidden: once a second the page catches up in the 30fps steps it plays in on screen, with no drawing, so raids, trips and the dragon arrive as they would have. With all of those off it pauses. The app tells the page when it hides the window (a `shown` event), as WebView2 doesn't set `document.hidden` for a hidden window on its own, and nothing in the app polls while it's hidden: the pointer watch and the native loops wait until it shows. `IDLE_FIGHTERZ_SMOKE=<file>` hides the widget 8 s after launch and writes what the page reports to the file, with the engine and whether the Rust core plays on hidden; the Windows and Linux smoke tests use it.
- **Ghost mode** (a setting and a tray item, off by default): the floating widget lets clicks through to whatever is under it (`set_ignore_cursor_events`), and holding ⌥ (Alt on Windows and Linux) makes it take them again while held; the HUD wakes as it does on hover, which is the cue. Ghosted, the pointer passing over it doesn't wake the HUD. ⌥ is read ten times a second, only while ghost mode is on and the widget shows, from state any app can read: `CGEventSourceFlagsState` on macOS (no event tap, so no Input Monitoring), `GetAsyncKeyState` on Windows, `XQueryPointer` on X11. Wayland shows an app no keys but its own, so there ghost mode is turned off from the tray. Window mode is unaffected. See `src-tauri/src/system.rs`.
- **Auto-hide** (a setting, on by default on macOS and Windows, off on Linux): the widget hides while a fullscreen app or a slideshow is in front and comes back after, through the same hidden path as × (the game keeps playing, notifications as usual). It acts on changes only: shown by hand during a slideshow, it stays. Checked every 2 s while the widget shows or is auto-hidden. macOS: the frontmost ordinary window fills a display (a fullscreen Space, a borderless game), or Keynote or PowerPoint fills one at any level; window bounds, owners and levels need no Screen Recording permission. Windows: `SHQueryUserNotificationState` says busy, a Direct3D game or presentation mode. Linux: the active window's `_NET_WM_STATE_FULLSCREEN` on X11; nothing on Wayland, where the setting isn't shown. Screen sharing alone isn't detected anywhere: no OS says so without a permission.
- **Battery saver when unplugged** (a setting, on by default): on battery or in low power mode, balanced (30fps) draws as battery saver (15), and goes back when plugged in. Smooth or battery saver picked by hand stays. Checked every 20 s while the widget shows. macOS: IOKit's providing power source and `NSProcessInfo.isLowPowerModeEnabled`; Windows: `GetSystemPowerStatus` (unplugged, or battery saver on); Linux: `/sys/class/power_supply` and power-profiles-daemon's power-saver profile.
- **Moving it**: press on empty sky and drag, or hold ⌥/⌘ and drag from anywhere. A click on the planet trains as usual.
- **Menu bar**: the scouter icon with your power level beside it (1.2K, 3.4M, 5.6B, then 7.8e12), updated about once a second and only when the number changes; a setting turns the number off and leaves the icon. Its menu: show/hide, settings, photo mode, always on top, ghost mode, size (small 300, medium 400, large 560 pt, and any size in settings), profiles, snooze notifications, launch at login, quit. Position and settings are kept between launches. The game isn't saved, same as on the site.
- **Profiles**: settings saves the current look and behaviour under a name ("work": small, ghost mode, quiet; "play": big, sound on); the tray's Profiles submenu switches between them and checks the one the settings match. A profile keeps size, opacity, layout, skin, theme, HUD, frame rate, mode, clouds, ghost mode, auto-hide, battery saver, the power level in the menu bar, notifications, quiet hours, focus, the away recap and the game's sound; not the shortcut, launch at login, updates, the tray icon's colour or a snooze. Up to 12, in `settings.json` (`profiles`).
- **Snooze** (tray): 30 minutes, 1 hour, 3 hours or until tomorrow (the next 8:00); the submenu shows the time left, with Resume. Kept in `settings.json` (`snooze_until`) so a restart doesn't end it.
- **Quiet in focus** (a setting, on by default): no notifications while the OS is in Focus / Do Not Disturb. Windows: Focus Assist / Do Not Disturb from its WNF state, else `SHQueryUserNotificationState`'s quiet time. Linux: GNOME's `show-banners` (through the settings portal, else `gsettings`), or KDE's notification server's `Inhibited`. macOS has no public way to read Focus without a permission prompt: the app reads `~/Library/DoNotDisturb/DB/Assertions.json` when it can (only with Full Disk Access, which macOS never prompts for), and otherwise leaves it to macOS, which holds the app's notifications back in Focus anyway (they go quietly to Notification Center). Settings says which ("on now", "off now", "can't tell here").
- **Snap and stay**: let go of the floating widget within 40 pt of a screen edge (or past it) and it snaps 8 pt in from that edge, or both edges near a corner. Where it's left is kept per arrangement of displays in `places.json` beside `settings.json` (16 at most); when the displays change it goes back to its place for the new arrangement, or is pulled wholly back on screen. Displays are checked every 3 s while the widget shows; a drag is over once the mouse button is up (read with `CGEventSourceButtonState`, `GetAsyncKeyState` or `XQueryPointer`, no permission). Not on Wayland, which tells no app where its window is.
- **Photo mode** (the tray, or P on the widget; Rust core only): the game pauses, the HUD steps aside, and the frame is saved as a PNG at twice its on-screen size in whole pixels (transparent round a floating planet), to the pictures folder (`~/Pictures`, the Windows Pictures folder, `XDG_PICTURES_DIR`) and the clipboard (PNG on macOS; PNG and a 32-bit DIB on Windows; GTK's clipboard on Linux). Any key or click carries on and a toast says where the photo went; the paused time is played then, so a photo costs the run nothing.
- **Away recap** (a setting, on by default; Rust core only): after 10 minutes or more with no keyboard or mouse input (idle or locked; `CGEventSourceSecondsSinceLastEventType`, `GetLastInputInfo`, X11's screen saver extension or GNOME's/KDE's idle time on Wayland), coming back shows one toast with what happened meanwhile: "while you were away: +2.1B power, beat frieza, the dragon is waiting". Only if something did, and only if the widget shows; nothing is kept on disk. Debug builds read the idle time from the file `IDLE_FIGHTERZ_IDLE` names, to try it without leaving the computer.
- **Settings window style** (`settings_style`, default `compact`): `compact` is the tall single column (settings.html); `full` (settings-full.html) is a wide window with tabs, a live preview (the widget's last frame from the Rust core, `preview_frame`, a few times a second while the window shows, under a drawing of the HUD in the picked layout, size, opacity and mode) and dark mode following the OS. Both offer every setting (a test in main.rs fails if one has a row the other lacks) and the switch: picking the other style turns the open window into it.
- **Menu-bar popover** (`tray_style`, default `menu`; macOS and Windows): `popover` makes a click on the tray icon open popover.html in a small frameless window under it (`popover.rs` places it by the icon's rect, the display's work area and the bar's edge, clamped to the display), with the power, form, next goal, dragon balls, quick toggles, the size and the usual items. Right-click (and ⌃-click on macOS) still opens the native menu. It closes on losing focus or Esc, and asks for nothing while hidden. Linux's AppIndicator reports no clicks, so there it's always the menu. Debug builds only: `IDLE_FIGHTERZ_DEBUG_OPEN=popover`, `menu` (the ⌃-click menu), `settings` or `settings:<tab>` opens it 3 s after launch, and `IDLE_FIGHTERZ_DEBUG_ICON=x,y,w,h` (physical pixels) stands in for the icon's rect: for testing with a menu bar that hides the icon.
- **First-run card** (`onboarded`, false only on a first launch): onboard.js (added to the widget's pages by scripts/pages.mjs) shows three steps where the dock goes; step 1 rings the planet where the core draws it (`planet_spot`: the camera's centre and radius, mapped onto the canvas, the same 9 points clear of the disc's outline at every size). The card goes above the planet when there's more room there (a top strip), and is shorter on a small widget. `sh scripts/ring-e2e.sh <bundle.app> <test identifier>` checks it on screen (macOS): it runs the bundle at 300, 400 and 720 pt in several layouts, on the layer and on the canvas, captures only the widget's own window once there's been no input for 30 s, and `scripts/ring-check.swift` fails if the gold ring is more than 2 pt off the drawn disc's centre or not 4 to 14 pt clear of it. Skip or finish calls `intro_done`. An existing settings.json without the key means an upgrade, so `prefs::migrate` sets it true; settings' "show the intro again" sets it false and shows the widget.
- **Icons**: `npm run icons` renders the pixel-art dragon ball app icon and the scouter tray icon (black `tray.png`, the macOS template image, and white `tray-white.png`) into `src-tauri/icons/`.
- **Rust core** (the default since 0.2): the `rust-core` cargo feature runs the game on `planet-core` in the app, draws it with `planet-render` (pixel for pixel what game.js draws), behind a HUD-only page, and saves it to a file. With `native-renderer` (macOS; also default), a floating widget shows the frames in a layer under that page instead of on its canvas, falling back to the canvas if the layer fails. `IDLE_FIGHTERZ_ENGINE=canvas` or `=web` (0.1's game.js in the web view) pick another path at launch. See [NATIVE.md](../NATIVE.md#what-ships-02).
- **Native renderer stand-ins**: a hidden setting that shows recorded frames or a test pattern in a `CALayer` instead of the web view. See [NATIVE.md](../NATIVE.md). See [NATIVE.md](../NATIVE.md#the-rust-core-feature-rust-core).
